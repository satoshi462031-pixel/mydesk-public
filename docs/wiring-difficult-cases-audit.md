# 配線図の難しいケースの調査

調査・修正日: 2026-10-11 / 初回調査: `02afd78` / 修正の比較元: `2dc7cfb`

## 結論

接続判定で3件の問題を最小構成で再現し、修正した。機器数の多さだけでなく、**同じ端子形状で能力が異なる場合、候補の広い機器と狭い機器が競合する場合、手動指定で上流の成立性チェックを通らない場合**に不自然な結果になる。

配置では400構成を検査した。高密度構成の中心的な課題は、同じ機器につながる線の交差、同じ2本の複数交差、往復する経路だった。今回の自動配置・サイズ変更の360構成では、監査基準に該当する完全重複・近接並走・機器貫通は検出されなかった。

製品コードの変更は`wiringEngine.ts`とキャッシュ版・事前生成データに限定した。配置の評価・探索・描画処理は変更せず、配置監査の短縮候補にあった誤検知を修正した。

## 既存実装と仕様の整理

1. `generateWiring`が登録日時・同時刻ならデスク選択順に候補を処理する。端子互換表、入出力、映像能力、使用済みの口を確認し、上流機器・映像・周辺機器・給電の順で接続を作る。映像は変換不要の同形状端子を優先する。
2. `reconcileMap`が自動下書きと既存データを突き合わせる。手動線・確定状態・破棄・分岐・ケーブル申告を引き継ぐ。接続先指定が成立しない画面は、従来から自動選択へ戻る。
3. `computeMapLayout`がカテゴリに基づく段配置、接続点割り当て、直交経路探索、交差・並走補修、短縮を行う。描画は通常画面と履歴画面で別だが、履歴の配置も同じ計算を使う。手動位置同士の重複は本人の指定として動かさない。

交差削減より線の重複解消を優先する場合があり、探索量・曲がり増加にも上限がある。この意図を保ち、交差数を下げるための探索拡大や配置全体の変更は行っていない。

## 再現した接続判定の問題と修正

以下の「実際」は修正前の挙動。行番号も修正前の参照位置。

### A — 映像非対応のUSB-Cまで映像出力として消費する（優先度: 高）

- 構成: PCのUSB-C出力が「映像対応1口 + 非対応1口」。USB-C映像入力の画面が2台。
- 実際: PCから両方の画面へUSB-C線を生成する。警告なし。
- 期待: 自動生成できる映像接続は1台分。2台目は未接続として案内する。
- 対照: 非対応USB-Cだけを除くと、接続は1台になり、2台目の警告が出る。
- 原因: `buildPortUsageMap` は種類と方向で残数を合算する。一方、`findAvailablePort` は映像対応の口が1つでも存在することと、種類全体の残数だけを確認する。対応口を使い切った後も、非対応口の残数を使えてしまう。
- 該当箇所: [wiringEngine.ts](../src/utils/wiringEngine.ts) の36〜47行、91〜113行。
- 修正: 残数を登録ポートごとに管理し、映像接続では映像能力を満たす口だけを探索・消費する。方向別の優先順位と双方向口の共有を維持。実際に消費した上流口が映像対応かどうかも記録する。外部のデータ型・保存形式は変更していない。

### B — 全画面を接続できるのに、先着割り当てで1台を取り残す（優先度: 中）

- 構成: PCのDP出力1口・HDMI出力1口、DP/HDMI両対応画面、DP専用画面。
- 実際: 両対応画面が先に処理されるとDPを消費し、専用画面が未接続。「方向性またはアクティブ映像変換が必要」と案内される。
- 期待: 両対応画面をHDMI、専用画面をDPにすれば追加機材なしで両方つながる。
- 対照: 専用画面を先に処理すると両方つながり、警告も消える。
- 原因: 画面ごとに最初の成立候補を選ぶため、後続画面の制約を見て割り当て直さない。
- 該当箇所: [wiringEngine.ts](../src/utils/wiringEngine.ts) の`findVideoPair`（647行付近）、画面ループ（769行付近）、候補確定（802〜810行）。
- 順序の条件: 実装は`createdAt`の古い順、同時刻では`selectedGadgetIds`の順で処理する。再現では同時刻に固定して選択順だけを変えた。単に`allGadgets`配列を並べ替える問題ではない。
- 修正: 単一PCからの自動接続で、未確定の画面に別の同形状端子も使え、専用画面を取り残す数が減る場合だけ代替端子を選ぶ。機器順の変更・全体の割り当て直しはしない。保存済みの確定・手動選択がある場合は調整を止め、生成したHDMI線を確定した後も同じ選択を保つ。指定先、複数PCの担当画面、変換優先度、破棄した線を尊重する。
- 範囲: 複数PCやDockを横断した全体最適化は行わない。この限定で再現ケースは解消するが、任意構成の最大接続数は保証しない。

### C — 映像が届かないDockを手動指定すると、成立したように見える（優先度: 高）

- 構成: PCに映像非対応USB-CとDP出力。DockにUSB-C入力とDP出力。DP画面の接続先をDockに指定。
- 実際: `PC → USB-C → Dock → DP → 画面`を生成。PC→Dockで映像を送れないが警告なし。
- 期待: 接続先指定にも上流の映像成立性を確認し、未成立を案内する。
- 対照: 指定を外すとPCから画面へDP直結になり、Dockからの映像線は生成しない。
- 原因: 指定画面の先行処理では`findVideoPair(source, display)`だけを確認する。通常の自動選択が使う`videoLinkedUpstreamIds`を確認していない。さらに`feedsDisplay`も、リレーをたどる際にそのリンクの映像能力を確認しないため、この経路を画面ありと扱う。
- 該当箇所: [wiringEngine.ts](../src/utils/wiringEngine.ts) の730〜748行、783〜785行、988〜1001行。
- 修正: `findVideoPair`に上流成立性の確認を集約し、指定されたDockも同じ確認を通す。成立しない指定は既存仕様に従い自動選択へ戻すため、このケースはPC直結になる。`feedsDisplay`も実際に映像を運べる線だけをたどる。破棄した上流線を接続済み扱いにする分岐も修正した。
- 維持した仕様: PC未登録のDock単独構成を映像源として扱う既存の仮定は変更していない。

3件とも3台だけで再現する。多機器構成では候補の競合や端子能力の混在が増えるため、同じ条件を含みやすい。

### 特に読みづらくなる構成

1. **2PC・3画面・Dock・複数Hub・複数充電器の集中**: `blog #62` は入力38台、表示37ノード、38エッジで51指摘。同じ機器を共有しない2本が3回交差する箇所もある。`blog #110`も38台で36指摘。
2. **信号線・電源線・周辺機器接続が画面周辺に集まる配信構成**: `real #99`は入力15台、16ノード、19エッジで21指摘。PCと画面の間の別々の線が2回交差する。30台以上でしか起きない問題ではない。
3. **ノードのサイズを大きく変えた構成**: `blog-size #55`は20台、20ノード、23エッジで40指摘。集約先周辺の線が複数の高さで横切り、接続先を追いにくい。
4. **手動移動後のノード重複**: `drag #33`でキーボードとマウスが47×68図座標重複。保存された移動量を適用した結果であり、自動配置だけの重複としては数えない。今回の40構成で線の機器貫通は検出されなかった。

これらは再現可能な読みづらさの候補。交差・折り返しがあるだけでは、避けられる不具合とは断定しない。[経路ルール](wiring-routing-rules.md)にも、交差の解消は目標であって保証ではないとある。

実装は交差補修を3パス・予算60、探索量をフェーズごとの上限で抑え、並走解消を交差削減より優先する場合がある（[connectionMapLayout.ts](../src/utils/connectionMapLayout.ts)の3345行、3641〜3643行、4173〜4186行付近）。残存する交差と整合する設計だが、今回の各ケースがどの上限・選択で残ったかまではトレースしていない。

### 配置監査で修正した誤検知

`real #29`のBluetooth線は118図座標短縮できると検出されていたが、代替経路の終端が`(349,369) → (349,364)`、長さ5になっていた。最低の出足13を満たさず、製品側で採用できる改善案ではない。監査の短縮候補に両端の最低長チェックを追加した。修正前後を個別再実行し、実際の配置・経路は同一で、この誤検知だけが消えることを確認した。

### 集計の限界

- `blog`と`blog-size`は乱数消費が異なり、同じ番号でも同一機器構成ではない。サイズ変更だけによる悪化量はこの表から断定しない。
- 非Wi-Fiの補助線も監査に含む。UIでは線種・描画順・交差の切れ目で読みやすさが変わる。今回は座標と接続データの検査で、実機画面の視認性評価は未実施。
- 既存監査は同一`sourcePortId`の組を並走検査から除外する。0件はその基準内の結果であり、すべての線の非重複を証明しない。
- ノード重複を許す手動配置の救済経路では貫通しうることが既存ルールに記載されているが、今回は貫通を再現していない。
