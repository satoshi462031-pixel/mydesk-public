# 拍手機能仕様（旧：いいね）

## 1. 目的

公開デスクの**更新**に対して、閲覧者が投稿者へ軽い称賛を送れるようにする。

- 拍手はデスクそのものではなく「その時点のデスク」への反応とする。機材や写真が変わるたびに、
  同じ人がもう一度拍手できる。
- 狙いは、更新 → 保存した人へ更新が届く → 拍手 → 投稿者に届く → また更新する、の循環を
  少人数でも回すこと。回数上限のある仕組み（ハイプ型）は利用者が少ない時期に差が出ないため採らない。
- 拍手は「反応」、保存は「あとで見返すための個人用管理」として役割を分ける（旧仕様から変えない）。

呼び方を「いいね」から「拍手」に変えたのは、件数を延べで数えるため（6.3）。
「いいね 128」は人数と読まれ、延べだと水増しに見える。拍手は何度も送るものなので延べと矛盾しない。

## 2. 用語

| 用語 | 意味 |
|---|---|
| 版 | 拍手を受け付ける区切り。機材か写真が変わった公開で新しい版になる（6.2） |
| 今の版 | デスクの最新の版。拍手の追加・取り消しは今の版にだけできる |
| 累計 | すべての版への拍手の延べ件数。表に出す件数はこれ |

## 3. 対象

- 拍手できるのは、他ユーザーが公開（`visibility = 'public'`）しているデスクのみとする。
  自分のデスク、URL限定、非公開、削除済みのデスクには拍手できない（旧仕様どおり）。
- 拍手の追加・取り消しにはログインが必要とする。
- 1ユーザーが1つのデスクの**同じ版**に送れる拍手は1件までとする。

## 4. ユーザー操作

### 4.1 未ログイン

- 拍手ボタンを押すとログイン案内を表示する。
- ログイン完了前は拍手状態と件数を変更しない。

### 4.2 ログイン済み

- 今の版に未拍手の状態で押すと、拍手を追加する。
- 今の版に拍手済みの状態で押すと、拍手を取り消す。
- 過去の版への拍手は取り消せない。過去の版は画面に出ないため、取り消す手段も設けない。
- 連打による重複リクエストを防止する。
- 操作直後は画面へ先に反映し、通信失敗時は元の状態へ戻す。
- 現在の状態を取得できていない場合は、状態を再取得してから反転する。

### 4.3 更新後の再拍手

- 前の版に拍手した人が更新後に開くと、ボタンは未拍手の見た目に戻る。
- 公開デスク詳細では、そのときラベルを「もう一度拍手」にし、読み上げは「デスクが更新されました。もう一度拍手する」とする。
  前の版に拍手していない人には出さない。フィードのカードはアイコンだけなので出し分けない。

## 5. 表示仕様

### 5.1 みんなのデスク

- 各カードの写真の右下に拍手ボタンと累計を表示する。状態は今の版に拍手したかで決める。
  （旧仕様は「件数を表示しない」だったが、実装は反応の手応えを見せるため件数を出していた。実装に合わせた）
- 拍手数をフィードの並び順には使用しない。

### 5.2 公開デスク詳細

- 固定アクション領域に拍手ボタンと「拍手」を表示する。累計が1件以上なら件数を併記する。
- 機材か写真が一度でも変わったデスクでは、用途と更新日の行の下に「最近の変化：モニターを入れ替え ほか2件」を出す。
  何に拍手しているのかが分からないと、更新ごとに拍手できる意味が薄れるため。
  算出は一覧のタイルと同じ `summarizeDeskChanges`、言い方はみんなのデスクの更新の行と同じくカテゴリで言う（`deskChangeHeadline`）。
  写真だけの変更は機材の履歴に残らないので、この行には出ない。
- 自分のデスクでは操作を無効にし、累計を表示する。今の版への件数は、持ち主向けの反応の行
  （マイデスク・公開デスクの管理の `reactionSummary`、ベル）に出す。

### 5.3 マイページ

- 拍手したデスクの一覧は設けない。後から見返したいデスクは「保存」を使用する。
- 保存したデスクの更新通知に、拍手しただけのデスクを含めない（旧仕様どおり）。

### 5.4 見た目

- アイコンは MaterialCommunityIcons の `hand-clap`（`ICONS` に登録して使う）。
- 拍手済みは手の後ろの丸を `clap`（黄）で塗り、手を `onClapFill` にする。未拍手は塗らず、手を `textMuted`。
  `hand-clap` には塗りと輪郭の2種類が無く、ハートのように形では示せない。手の色だけだと
  黄は白い面で 3:1 に届かず、ダークでは灰色の手と明度が近いので、塗った面の大きさで色以外の手がかりを作る
  （X のハートが輪郭から塗りに変わるのと同じ役割）。ラベルは「拍手」のまま変えない。
- みんなのデスクの写真の上では暗い丸の地に載るので丸は塗らず、拍手済みは手を `onClap` にする。
  読み上げには選択状態で伝える。
- 拍手したときの演出（`ClapBurst`）は X のいいねの時間割に倣う。手が一度消え、塗りの泡が広がって輪になり、
  粒が散ってから手が弾んで戻る。取り消しでは演出しない。動きを減らす設定では演出しない。
- 件数が変わるときは、増えたら上へ・減ったら下へ数字を送る（`RollingCount`）。
- 英語 UI は「Applause」。

## 6. 版と件数

### 6.1 版の持ち方

- デスクは今の版の開始日時（`desks.clap_round_at`）を持つ。拍手はどの版に送ったか（`likes.round_at`）を持つ。
- 既存の公開デスクの `clap_round_at` は `COALESCE(content_updated_at, created_at)` で埋める。

### 6.2 版が切り替わる条件

- 切り替えの契機は `desks.content_updated_at` が進んだとき（機材か写真が変わった公開）とする。
  題名・説明文・表示名だけの変更では切り替えない。
- ただし今の版の開始から **24時間未満** の更新は同じ版にまとめる。
  短い間隔で何度も更新されたとき、閲覧者の拍手ボタンが何度も未拍手へ戻らないようにするため。
- 切り替えはサーバー側のトリガで行い、クライアントが書いた値は採用しない（`content_updated_at` と同じ理由）。
- 公開範囲の変更（非公開 → 公開など）では切り替えない。

### 6.3 件数

- `desks.like_count` は累計（延べ）とする。同じ人が3つの版に拍手すれば3と数える。
- 更新で件数をリセットしない。表の件数が減るなら更新を控える、という逆向きの動機を作らないため。
- 増減は旧仕様と同じく `likes` の追加・削除に連動した DB トリガで行い、クライアントからの直接更新を許可しない。
- 拍手数だけが変わった場合は `desks.updated_at` を更新しない（旧仕様どおり）。

## 7. プライバシー

- 公開するのはデスクごとの累計件数だけとする。
- 誰がどのデスクのどの版へ拍手したかは、拍手した本人だけが取得できる。
- 投稿者にも、拍手したユーザーの一覧や識別情報を公開しない。
- 匿名ユーザーには拍手レコードの読み書きを許可しない。

## 8. データ仕様

### 8.1 likes

| 項目 | 内容 |
|---|---|
| `id` | 拍手ID |
| `desk_id` | 対象デスクID |
| `user_id` | 操作ユーザーID |
| `round_at` | 拍手した版の開始日時（追加） |
| `created_at` | 作成日時 |

- 一意制約を `(desk_id, user_id)` から `(desk_id, user_id, round_at)` に変える。
- `round_at` はサーバーが追加時の `desks.clap_round_at` で埋める。クライアントが指定した値は採用しない。
- 既存の行は、各デスクの今の版（`clap_round_at`）で埋める。リリース直後に全員の拍手ボタンが
  未拍手へ戻るのを避けるため。
- 削除は本人の、今の版の行だけを許可する（RLS）。
- デスクまたはユーザーの削除時は関連する拍手を削除する。

### 8.2 内部名は変えない

テーブル `likes`、列 `like_count`、関数名、計測イベント `like_toggled` は名前を変えない。
導入前後の計測を1本の系列でつなぐためである。コード上の `plan` がデスクの旧称であるのと同じ扱いとし、
実装時に CLAUDE.md の「画面の名前」に対応を書く。

## 9. 通知

- 投稿者向けにはベルの「反応」で、前に見たあとに増えた拍手をデスクごとに集約して届ける
  （`get_my_desk_reactions`・086）。今の版への件数も返し、「この更新に N件の拍手」と出せるようにする。
- プッシュ通知も送る（096・`notify-claps`）。旧仕様は送らなかったが、アプリを開かない投稿者に
  反響が届かないと、更新 → 拍手 → 投稿者に届く、の循環が切れる。
  - 拍手が新しく入るたびにアプリが頼み、送るかはサーバーが決める。最初の1件はすぐ送り、
    同じ持ち主へは12時間に1回まで（持ち主単位。デスクを複数公開していても鳴り続けない）。
  - 文面は「「デスク名」に新しい拍手が N件届きました」。N は前の通知以降に対象デスクへ届いた件数。
  - 持ち主がブロックした人・持ち主をブロックした人の拍手は数えない。
  - 設定の「通知」で止められる（`notification_prefs.claps`）。
  - 許可のダイアログは、デスクを初めて公開した直後（`PublishModal`）と、設定の「通知」から出す。
- どの通知にもユーザー名は含めない。

公開スイッチは現在オフ。iOS通知の文面・条件・公開手順は `docs/ios-push-notifications.md` を参照する。

## 10. アクセシビリティ

- 未拍手時のラベルは「拍手する」、拍手済みは「拍手を取り消す」とする。
- 4.3 の「更新されました」は読み上げ対象に含める。
- 詳細画面では累計件数を読み上げ対象に含める。
- 選択状態（`accessibilityState.selected`）を必ず付ける。見た目で色以外の手がかりがあるのは詳細画面のラベルだけ（5.4）。

## 11. 計測

### 11.1 イベント

- 追加・取り消しの成功時に `like_toggled` を記録する（名前は変えない）。
- 送るのは `liked`・操作箇所（`desk_feed` / `public_desk`）・`repeat`（前の版にも拍手していたか）。
- 対象デスクIDや投稿者IDは分析イベントへ送信しない（旧仕様どおり）。

### 11.2 成功の判定

1. **公開デスクの更新間隔が縮むか。** `desk_publish_log` の `content_changed = true` の行の間隔の中央値。
2. **再拍手率。** ある版に拍手した人のうち、次の版にも拍手した人の割合。

リリースと同時に入れるため「導入前」の利用データは無い。この設計は計測からではなく、
「開発中の段階で反応を活発にするには」という仮説から決めた。
そのため 1 は「拍手を受け取った更新」と「受け取らなかった更新」で、次の更新までの間隔を比べる。
活発な人ほど拍手も受け取るので因果は弱く、傾向を見る材料として扱う。

## 12. 対象外

- ガジェット単位の拍手
- 拍手したユーザー一覧・拍手履歴一覧
- 過去の版の表示と、過去の版への拍手の取り消し
- 拍手数によるランキングや並び替え
- 回数上限のある拍手（ハイプ型）
- 拍手を条件にした更新通知
- 投稿者から閲覧者へのリアクション返し

## 13. 受け入れ条件

1. 認証済みユーザーが他人の公開デスクの今の版へ拍手を追加・取り消しできる。
2. 同一ユーザーが同じ版へ重複して拍手できない。
3. 版が切り替わった後、同じユーザーがもう一度拍手でき、累計が1増える。
4. 今の版の開始から24時間未満の更新では版が切り替わらない。
5. 題名・説明文だけの変更では版が切り替わらない。
6. 過去の版への拍手は取り消せない。
7. 未ログイン、自分のデスク、URL限定・非公開デスクへの追加が拒否される。
8. 累計は追加で1増え、取り消しで1減り、0未満にならない。更新で減らない。
9. 拍手操作だけではフィードの更新順が変わらない。
10. 他ユーザーの拍手レコードを取得できない。クライアントから `round_at` を偽れない。
11. 一覧と詳細で拍手状態が再表示時に一致する。
12. 通信失敗時に楽観更新が取り消され、再操作できる。
13. 前の版に拍手した人にだけ「更新されました」が出る。
14. 既存のいいねは移行後、今の版への拍手として拍手済みで表示される。
