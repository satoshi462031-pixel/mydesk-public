---
description: アプリ内フィードバックを取り込み、束に振り分けて、対応の順を決める
argument-hint: （省略可）done <束のキー> ＝修正を入れた束を対応済みにする / release <版> ＝その版で直した束を並べる
---

引数: **$ARGUMENTS**

状態は `.feedback/ledger.json`（台帳）に持つ。`items` が取り込んだ全件、`clusters` が束
（同じ不満・同じ不具合のまとまり）。`npm run feedback:pull` が新着を `cluster: null` で足し、
このコマンドが振り分けと状態を書く。**台帳から item を消さない**（件数と再発の判定が壊れる）。

引数によって次のどれか1つをやる。

## 引数なし：取り込みと振り分け

### 1. 取り込む

`npm run feedback:pull` を打つ（打てなければユーザーに頼んで待つ）。「新着も未分類の持ち越しも無い」なら
そう報告して終わる。出たら `.feedback/` の最新の `.md` と `ledger.json` を読む。

### 2. 「要確認」を先に見る

- **再発の疑い**：修正より後に作られたバンドル（ストアのビルドか OTA 更新）から、同じ束に報告が来ている。
  本文と直前の操作を読み、本当に同じ症状なら束を `open` に戻して `note` に「◯月◯日のバンドルで再発」と
  書き、`fixedAt` / `commit` は次に直したときに書き換える。別の症状なら別の束に移す。
- **修正の前後を判定できない**：バンドルの情報が無い送信（094 より前・開発ビルド）で、版番号も修正版と同じ。
  本文から判断できなければそのままにしてよい。
- **台帳に無い束のキー**：手で書いたときの打ち間違い。正しいキーに直す。

### 3. 振り分ける（新着と持ち越しの全件）

- **既存の束に入るかを先に考える。** 新しい束を作るのは、既存のどれとも原因・要望が違うときだけ。
  言い回しが違っても、同じ画面の同じ操作で困っているなら同じ束にする。
- 束のキーは kebab-case の英語（`photo-upload-fails` など）。`title` は日本語で短く。
- 送信時のカテゴリ（不具合／要望）は送った人の自己申告なので、そのまま束の `kind` にしない。
  本文と直前の操作から判断する（「◯◯できない」が仕様どおりの動きなら要望）。
- **対応済み（`done`）の束に入れたら、修正の前後は `feedback:pull` が次回判定する**（`regressionStatus`）。
  版番号では判定しない。修正は同じ版番号の OTA 更新でも届くので、同じ 1.0.0 に直す前と後が混ざる。
- 本文だけでは何のことか分からないものは、無理に束にしない。`cluster: null` のまま残して
  報告で「判断できなかった」と挙げる（次回も持ち越しに出る）。

### 4. 束の状態を決める

- **不具合**
  - 直前の操作の画面名（ルート名）と失敗イベント（`operation` / `code`）から画面と処理を特定する。
    ルート名は `src/types/index.ts` の `*ParamList` と CLAUDE.md の「画面の名前」の表で実装に引き当てる。
    疑わしいコードの場所と再現手順を `note` に書く。
  - 「Sentry の直近の事象」があれば、その ID の事象（スタックトレース）を Sentry で見るようユーザーに伝える。
  - 環境（OS・iPad・言語・外観・プラン）で絞れる症状か見る（iOS 26 だけ・英語だけ・Free だけ、など）。
  - 再現の手がかりが足りなければ `watching` にして、何が足りないかを `note` に書く。
    推測で原因を断定しない。返信の手段が無く聞き返せないので、同じ束に次の報告が来るのを待つ。
  - 手がかりがあるものは `open`。
- **要望**
  - 製品の軸は「デスクの共有」。配線への要望が多くても、それだけで配線を主役にする判断はしない。
  - 軸に沿うか、既に同じことができる導線が無いかを見る。導線が見つからないだけなら、それ自体を不具合の束にする。
  - 1人の要望は `watching`。**別々の3人以上**から来たら `open` を検討する。
  - 軸から外れるものは `wontfix` にして、理由を `note` に書く。
- `open` にするかどうかは提案までにとどめる。決めるのはユーザー。

### 5. 台帳に書く

`ledger.json` を Edit で更新する。

- 変えてよいのは `items[id].cluster` と `clusters` だけ。それ以外の項目は `feedback:pull` が管理する。
- 書き終えたら `node -e "JSON.parse(require('fs').readFileSync('.feedback/ledger.json','utf8'))"`
  で JSON が壊れていないことを確かめる。

### 6. 報告

- 新着の振り分け結果。どの束に何件入ったかを書き、1件ずつ並べ直さない。
- 件数や人数が増えた束。
- 再発の疑いと、判断できなかった件。
- 対応を推奨する順に3束まで挙げる。それぞれ根拠（人数・影響する画面・直す規模）を1行で書く。

**ここでは直さない。** ユーザーが選んだ束だけを、不具合なら `/bug <領域>`（配線なら `/wiring`）で、
要望なら通常の設計相談の手順で進める。

## `done <束のキー>`：修正を入れた束を閉じる

修正のコミットが済んでから行う。`clusters[キー]` を次のように更新する。

- `status: "done"`
- `commit`：修正のコミットの短いハッシュ
- `fixedAt`：そのコミットの時刻（`git show -s --format=%cI <hash>`）。再発の判定に使うので必ず入れる。
  これより後に作られたバンドルからの報告を再発とみなす。
- `fixedIn`：修正を含む最初のストアの版。「新機能」の下書きにだけ使う。
  - `app.json` の `expo.version` を見る。まだストアに出していない版ならその版にする。
  - 既に出した版なら、OTA で出すなら同じ版、ストアに出すなら次の版にする。どちらか分からなければユーザーに聞く。

## `release <版>`：その版で直した束を並べる

`fixedIn` がその版の束（`done`）を並べる。そこから App Store の「新機能」の下書きを書く。

- フィードバックへの返信の手段がアプリに無いので、「ご意見から直したこと」を伝えられる場はここだけ。
- 書き方は利用者の言葉に寄せる。本文を引用したり、送った人を特定できる書き方はしない。
