対象領域: **$ARGUMENTS**

引数が空のときは、対象領域を**今セッションで変更したファイル全体**とする。
`git status --short` と `git diff` で変更箇所を列挙し、それを領域として扱う
（コミット済みのものも含め、この作業で触った範囲すべて）。

この領域に関するバグを洗い出して修正する。以下の観点を**すべて**通してから報告すること。

## 1. 調査（先に読む・まだ直さない）

関連ファイルを特定してから、次の観点で順に確認する。

- **状態の不整合** — context / store と永続化データ（Supabase・AsyncStorage）でズレる経路はないか
- **キャッシュ** — 計算結果をキャッシュしている箇所で、入力が変わったのにキーが変わらない経路はないか
- **キャッシュした結果の中のコピー・手で並べたキー** — キーが計算の入力を網羅していても、
  結果の中に入力のコピー（`edge.conn` / `node.gadget` 等）が入っていれば、キー外の項目は
  古いまま返る。描画や書き戻しがそのコピーを読んでいないか。キー・指紋・依存配列を
  項目を並べて作っている箇所は、実際に読んでいる（公開している）項目と突き合わせる
  （配線図のノードは、線を直した回の横展開で `edge.conn` の名前だけを探して漏れていた。
  配線の再計算キー・公開の指紋も、並べた項目が読んでいる項目より少なくて古い値が出ていた）
- **メモリ優先のストアを通さない読み込み** — `loadPlans()` / `loadGadgets()` をストアの外で
  直接呼んでいないか。保存はメモリが先・ディスクが後なので、直前の変更を読み落とし、
  読んだあとの変更も反映されない（AI コーチがこれで古い構成を送っていた）
- **デスクごとの派生値と生の値の取り違え** — 配線を組む・数える処理に、`applyDeskGadgetUsage` を
  通したガジェット（このデスクでは飾り、等）を渡しているか。同じ関数の中で通している
  呼び出しと通していない呼び出しが混ざっていないか（線を消したときの作り直しだけが生の値で、
  飾りの機材に線が引かれていた。隣に自分で処理を足した回にも気づけなかった）
- **保存時点の最新に載せ直さない書き戻し** — 画面が持っている値から作った「全体」を丸ごと
  保存していないか（配列・オブジェクトを渡す `onChange(next)`、`update({ ...snapshot })`）。
  裏の再計算など別の書き手と重なると、相手の保存を黙って消す。`updateWith` の中で
  最新の値に当てる「差分の関数」で渡す（配線図の編集が再計算の結果を上書きしていた）
- **境界値** — 0件・1件・大量（100件以上）・未ログイン・オフライン・無料プランでの挙動
- **「読めなかった」と「0件」の取り違え** — 読み込みの失敗を `catch { return [] }` や
  「件数が0なら待つ」で代用していないか。空を正として保存・公開・バックアップすると全件が消え、
  逆に0件を「まだ読めていない」扱いにすると本当に0件になった状態が永久に反映されない。
  失敗は例外か `loadFailed` の印で運び、再試行が成功したら空のメモリではなく読めた中身を採る
  （デスクだけ対策してガジェット・会話に横展開しておらず、再試行の復帰も空のまま保存を解禁していた。
  配線の作り直しも「0台なら線を残す」で読めていない場合を代用し、全部外したデスクに線が残った）
- **外部 SDK・API を実物の仕様どおりに使っているか** — 戻り値の形・禁止条件・イベントの意味を、
  モックや記憶ではなく `node_modules` の型定義と公式ドキュメントで確かめる。モックが実物と違う形を
  返していると、手元では動くのに実機でだけ壊れる（RevenueCat のリスナー解除は `{ remove }` を返す
  モックに合わせて書かれ、実物では一度も解除されていなかった。Webhook もイベントの意味を推測し、
  支払いの猶予期間中の人を free に落としていた）
- **旧データ** — 古い保存データに新しいフィールドが無い場合のフォールバック。`??` で握りつぶして
  誤った既定値になっていないか
- **ダークモード / ja・en 両方**での表示崩れ
- **プラン制限** — 無料 / Pro の分岐が `useEntitlement` 経由で一貫しているか
- **上限を入口でだけ守っている機能に、別の入口が無いか** — 上限の判定が作成の流れの中ではなく
  入口のボタンにある場合、あとから足した入口（設定の案内・コピー・再開）は判定を通らない。
  行き先の画面名でコードベース全体を検索し、入口ごとに判定の有無を並べる（設定の「使い方ガイド」が
  新しいデスクを作らせるのに `maxWiringPlans` を見ておらず、無料の上限を超えて作れた。
  「プラン制限」の観点は判定の書き方の一貫性しか見ておらず、判定が無い経路は拾えなかった）
- **画面遷移** — 戻るボタン・ディープリンク経由での到達時に前提が崩れないか
- **サーバー側の検証の厳密さ** — RPC / RLS / CHECK が、外から渡る値を先頭固定で見ているか。
  URL・ID・パスの照合が部分一致（`POSITION` / `LIKE '%..%'` / `includes`）になっていないか。
  そもそも検証が無い挿入経路が無いか（064 の穴はこの観点が無くて素通りしていた）
- **監査・検査コードそのものが対象を捕まえているか** — 0件の報告は「問題なし」と
  「何も見ていない」を区別できない。正規表現やパスを組み立てて対象を探す検査は、
  **意図的に壊した入力で1件でも拾えること**を先に確かめる
  （`auditSpacing` はテンプレートリテラルの `\s` が `s` に潰れて全画面をスキップし、
  ずっと「問題なし」を返していた。この観点が無くて素通りしていた）
- **公開前にクライアントが何を検査しているか** — 公開スナップショットに載る値と、
  モデレーション（`assertPublicContentAllowed`）に渡している値が一致しているか。
  除外リスト方式で公開範囲を決めていると、自由記入欄を足すたびに無検査で公開される
  （サーバー側の検証とは層が違うので、前の観点では拾えなかった）
- **公開範囲を絞るフラグを、あとから足した集約・検索の経路が見ているか** — 閲覧側から
  join できない設定は、非正規化したフラグ（`desks.owner_profile_public` 等）を
  経路ごとに参照する形になる。既存の読み出しに `.eq()` があっても、後から足した RPC には
  書き忘れる。フラグの列名でマイグレーション全体を検索し、公開データを返す関数と
  突き合わせる（079 の人の検索が 057 の設定を見ておらず、非公開にした人が
  名前・アイコン・公開デスク件数つきで検索結果に出ていた。値の検証を見る
  「サーバー側の検証の厳密さ」では、可視性フラグの参照漏れは拾えなかった）
- **読めなかったものを空として扱う代用が、絞り込みを外していないか** — `catch(() => [])`
  で潰しているのが「表示する中身」ではなく「除外リスト」のときは、失敗が
  フィルタの無効化になる。ブロック・ミュート・非表示の一覧を読む箇所は、
  失敗を一覧の読み込み失敗として扱う（`getBlockedUserIds` の 8 箇所すべてが
  空 Set にフォールバックし、読めないとブロックした相手が出ていた）
- **保存データの修復が、読む側で素で使うフィールドを全部補っているか** — 修復
  （`utils/storedDataRepair.ts`）が補う項目と、読み込み直後の並べ替え・描画が無防備に触る項目
  （`.localeCompare` / `.map` / `.includes` の前に `?.` や `?? ''` が無いもの）を突き合わせる。
  欠けた1件で読み込みそのものが例外になると「読めない」扱いで保存まで止まる
  （機材の `createdAt`・デスクの `updatedAt` が漏れていた。「読めなかった」と「0件」の観点は
  失敗の扱い方しか見ておらず、修復の取りこぼしで失敗が起きる向きを拾えなかった）
- **外から来た配列を、配列かどうかだけでなく要素まで確かめているか** — 公開デスクの
  `share_snapshot` は誰でも任意の JSON を書ける。`Array.isArray` を通しても、要素に `null` や
  文字列が混ざれば `c.fromGadgetId` / `period.startedAt` / `name.startsWith` で落ちる。配列は
  `objectArray`、機材は端末と同じ `repairStoredGadgets`、利用期間は `repairGadgetUsage` に通す
  （公開デスクは配線・利用期間・機材名の要素を見ておらず、壊れた1件で開いた全員の画面が落ちた。
  前の観点は端末の保存の「項目」を見ており、外部データの「要素」と、修復を通っていない入口を拾えなかった）
- **メモリを空にしてから外のデータを書き戻す処理が、途中の失敗でも合わせ直すか** — `clear*Cache()` は
  保存の停止まで解くので、書き戻しの途中で例外が出てディスクから読み直さずに抜けると、空のメモリが
  正のまま残って次の1回の編集で全件が消える。合わせ直し（`reload*FromDisk`）は `finally` に置き、
  落ちうる下ごしらえ（修復・写真の確認）はメモリを空にする前に済ませる（バックアップ復元がこれだった。
  「読めなかった」の観点は読み込みしか見ておらず、書き戻しの失敗経路を拾えなかった）
- **`CREATE OR REPLACE` で何度も書き換わる共有関数が、前の版の条件を落としていないか** —
  マイグレーションは追記しかできないので、同じトリガ関数が版を重ねる。後の版は直前の版
  ではなく「自分が参考にした版」を下敷きに全文を書き直すため、間に入った別の目的の条件が
  黙って消える。関数名でマイグレーション全体を検索し、**全版を並べて条件の差分を取る**
  （`update_updated_at` は 6 版あり、054 が足した `like_count` の除外を 057 が落として
  いた。いいね 1 つでデスクがフィードの先頭に上がっていた）。
  除外する項目を「条件式」と「`to_jsonb` からの減算」のように 2 箇所へ書く形は、
  片方を書き忘れて落ちる。1 箇所に並べる形へ寄せる
- **比べている 2 つの時刻の出どころが揃っているか** — 端末の時計で作った時刻
  （`new Date().toISOString()`）を、サーバー由来の時刻（`updated_at` /
  `content_updated_at`）と大小比較していないか。時計がずれている端末では、
  そのずれ幅ぶん判定が狂う（ベルの既読 `markBellSeen()` が端末時刻で、
  比較相手の `content_updated_at` はサーバー時刻。時計が進んでいる端末では
  その差のあいだに来た更新の点が出なかった）。保存する側と比べる側の両方を
  見て、**サーバー時刻同士か端末時刻同士のどちらかに寄せる**
- **日付だけの文字列を `new Date()` に渡していないか** — `new Date('2026-09-12')` は仕様で
  UTC 00:00 と解釈されるので、UTC より西の端末ではローカル時刻が前日になる。読み戻しが
  `getDate()` 系（ローカル）だと、開いて確定しただけで保存値が1日巻き戻る
  （購入日・撤去日の日付ピッカー 4 箇所がこれで、日本では起きずアメリカでだけ起きた）。
  暦日として扱う文字列は `parseLocalDate()`、ISO の瞬時から暦日を得るなら
  `calendarDateOf()` / `localDateKey()` を通す。逆向き（`toISOString().slice(0, 10)`）も同じ罠。
  **TZ に依存する回帰テストは、正と負のオフセットを両方固定する** — 片側だけだと
  反対側のバグが素通りする（`deskUsageDates.test.ts` は `Asia/Tokyo` だけを見ていた）
- **言語で差し替える表が、表示している項目を全部覆っているか** — ja / en の分岐は画面の文言
  だけでなく、ID で英語へ差し替える表（公式デモ）・画面の外で決まる文言（iOS の権限ダイアログは
  `app.json` の `locales`）・AI へ送る文面（通貨・ラベル）にもある。表を引いている項目と、実際に
  画面・外部へ出している項目を突き合わせる（デモは名前だけ英語化され、メモ・型番が日本語のまま
  英語画面に出ていた。写真の権限文言は日本語だけで、英語の端末にも日本語で出ていた。
  「ダークモード / ja・en 両方」の観点は画面の見た目しか見ておらず、データと外部向けの文言を拾えなかった）
- **入力中のフォームを、保存済みの値で上書きする経路が無いか** — 保存値を入力欄へ流し込む
  effect の依存に、ストアのオブジェクト・配列の参照（`deskPlan?.gadgetUsage` 等）を入れていないか。
  その表は無関係な項目の更新でも作り直されるので、裏の保存1回で入力中の全項目が戻り、
  「変更あり」の基準も取り直されて破棄確認も出ない（ガジェット詳細は、外した枠の後始末が
  裏で走ると入力が消えていた）。依存は id か値にする。あわせて、ある操作が関係の無い入力まで
  消していないか（カテゴリ変更で商品名を空にしていた）、下書きが入力の一部しか控えていないか
  （商品名だけ控えて、選んだ商品を落としていた）も見る。「状態の不整合」「保存時点の最新に
  載せ直さない書き戻し」はストア側の食い違いしか見ておらず、画面の入力が消える向きを拾えなかった
- **説明文が指している操作が、その時点の画面に出ているか** — 案内・ヒント・空状態の文言が
  言っているボタン名・タブ・操作と、その画面が実際に開く状態（初期タブ・ボタンの表記）を突き合わせる。
  画面側の既定を変えた回に、別ファイルにある文言は追従しない（作成直後は機材タブに着地するよう
  変えたのに、使い方ガイドの最後のカードは配線図の「線をタップ」を言い続けていた。
  「言語で差し替える表」の観点は訳が揃っているかしか見ておらず、中身が画面と合っているかは拾えなかった）
- **入力欄の `onChangeText` が、保存・取り消しの控え・計測を1打鍵ごとに発火していないか** — 文字を
  打つ欄は下書き（ローカルの state）に置き、欄を閉じる・別の操作をするときに1回だけ保存する。
  打鍵ごとに保存すると、取り消しの控えも1文字前で取り直すので「取り消す」で最後の1文字しか戻らない
  （配線の取り回しメモが1文字ごとにデスクを丸ごと保存していた）。`onChangeText` の呼び先を
  `set○○` 以外まで辿る。「保存時点の最新に載せ直さない書き戻し」は上書きの向きしか見ておらず、
  保存の回数と取り消しの単位は拾えなかった
- **上限を超えた値を `maxLength` 付きの欄へ流し込んでいないか** — iOS は「上限 − 今の長さ + 置き換える
  範囲」が 0 以下の変更を丸ごと拒むので、超えた値が入った欄は入力も Backspace も効かず固まる。
  上限をあとから入れた欄では、それより前に保存した長い値（商品名・メモ）がこれになる。
  `TextField` は `inputMaxLength` で守っているが、素の `TextInput` に `maxLength` を書くときは
  同じく通す。長さは UTF-16 で数える（`truncateChars` の文字数とは絵文字でずれる）。
  「入力中のフォームを保存済みの値で上書きする経路」は値が戻る向きしか見ておらず、
  値は正しいのに欄が固まる向きを拾えなかった
- **打つたびに区切りを挿す欄で、区切りだけを消した編集が整形で元に戻らないか** — `onChangeText` で
  3桁区切りなどを付け直すと、区切りの直後の Backspace は「,」を消すだけなので付け直して元の値になる。
  iOS はカーソルを末尾からの距離で保つためカーソルも戻り、何度押しても前の数字が消えない
  （金額欄。`priceDraftAfterEdit` で読み替える）。入力の観点は打つ向きしか見ておらず、消す向きで
  整形がどう戻るかは拾えなかった
- **画面に出していない項目の既定値が、答えとして保存・適用されていないか** — 「既定値＋編集」を
  まとめて作る関数（`specFor` 等）は、その画面で聞かなかった項目の既定値も返す。それを実物へ当てると、
  聞いていないのに上書きする（作成直前の「実物に合わせる」は、商品を選んだモニターの口数を隠していたが、
  アームを聞くためにページへ載せた答えに口数の既定値が入り、商品の端子を枠の標準に書き換えていた）。
  表示の出し分けと、適用する値の組み立てが同じ条件で絞られているかを突き合わせる。
  「入力中のフォームを上書きする経路」は保存済みの値が戻る向きしか見ておらず、既定値が進む向きを拾えなかった
- **ポートの有無を状態（載っている・使っている）として読むとき、そのポートを既定で付ける生成経路が無いか** —
  `armMountCategory` は受け口の有無を「アームを使用」と装着の印に使うが、作成フローの枠は受け口を
  常に持っていて、アームの無いデスクのモニターにも印が出ていた。登録済みの機材から選ぶと、
  持っていないアームまで作られた。読む側の関数名（`armMountCategory` / 受け口の `type` と `direction`）で
  検索し、同じポートを付ける生成側（`PLACEHOLDER_PORTS`・プリセット・商品の取り込み）と並べる。
  データ側の観点は保存値の食い違いしか見ておらず、生成の既定が意味を持つポートを拾えなかった
- **入力欄を押したとき、欄と押し上げた先がキーボードの上に見えているか** — RN は ScrollView の中の欄を
  自動では送らない。入力欄のある画面・シート・モーダルごとに「押し上げ（`KeyboardAvoidingView` /
  `BottomSheetModal` の `avoidKeyboard`）」「押した欄までのスクロール（`useKeyboardReveal` /
  `automaticallyAdjustKeyboardInsets`）」「どちらも無い場所（畳む上部・中央のダイアログ）」を並べ、
  欄が下のほうにあるものを iPhone SE の高さ（キーボード上端 407pt）で見積もる。あわせて
  「次へ」キーが次の欄へ移るか、候補を選んだあと欄が選ばれたまま残らないか、会話の一覧が
  縮んだとき下端に追従するかも見る（配線図の線の編集シート・写真の段の説明欄・デスク画面の
  ひとこと・名前の変更ダイアログが隠れていた。キーボードの観点がリストに無かった）
- **連打したとき、同じ画面が2枚積まれないか** — `navigation.push` は呼ぶたびに積む（`navigate` は積まない）。
  `grep -rnE "navigation\.push\(" src` の全件に、1回目で前面から外れた2回目を捨てる
  `navigation.isFocused()` の判定があるかを見る（公開デスク・プロフィールにだけ入れて横展開しておらず、
  みんなのデスク・更新・機材のシートなど13か所で2枚積まれた。保存の二重実行は見ていたが、遷移の連打は観点に無かった）
- **待ち終わりの `goBack` / `replace` が、待つ間に閉じた画面から呼ばれないか** — React Navigation 6 の
  `goBack` は送り元を見ず、その時点で一番上の画面を閉じる（`StackRouter` の POP は target が無いと
  `state.index` を使う）。保存・削除・購入の `await` の後に遷移している箇所を
  `grep -rnE -B4 "navigation\.(goBack|replace|pop)\(" src` で引き、`await` の後なら `navigation.isFocused()` を
  確かめているかを見る（機材の保存中にネイティブの戻るで離れると、保存後の `goBack` が配線図の画面まで閉じた。
  連打の観点は自前のボタンしか見ておらず、ネイティブの戻る・左端のスワイプと非同期の組み合わせを拾えなかった）
- **ジェスチャーを指ごとに作っていて、状態は1つしか持っていない箇所が無いか** — 普通のボタンは JS の
  responder が1つに絞るが、gesture-handler のジェスチャーは別の指・別のビューなら UIKit が同時に通す。
  `grep -rnE "Gesture\.(Pan|Tap|LongPress|Pinch)\(" src` の全件で、共有の state / ref（掴んでいる対象・移動量）に
  書くものが2本の指で同時に始まったときを考える（配線図で2つの機材を同時に掴むと、後に離した方が先の移動を消した）。
  あわせて、操作の途中で `GestureDetector` を条件で外す箇所（`active ? ... : ...`・条件付きの描画）を探す。
  外すと gesture-handler はコールバックの登録を消すので `onFinalize` が来ず、`onStart` で立てた印が残る
  （配線図は掴んだまま別の指でタブを切り替えると、機材がずれたまま残り、以後どれも掴めなくなった）。
  `.enabled(false)` への切り替えは取り消しとして `onFinalize` まで届くので対象外
- **入力の途中で戻る・タブ・進捗バーで離れたとき、入力が黙って消えないか** — 入力欄のある画面ごとに
  「離れるときに保存する」「確認する（`useConfirmDiscard` / `confirmDiscardChanges`）」「控えに残す」の
  どれかがあるかを並べる。写真をその場で保存する画面で名前と説明だけ「完了」でしか保存せず、
  デスク画面の編集は確認なしに捨てていた。保存の競合（ストア側）は見ていたが、画面を離れる操作は観点に無かった
- **ログアウトで消すものに、メモリにだけ持つ値が入っているか** — `clearLocalUserData` は AsyncStorage と
  ストアのキャッシュを消すが、モジュールの `let` に持つ控えは個別に消す必要がある。
  `grep -rnE "^(let|const) [a-zA-Z]+(: [^=]+)? = (null|new Map|new Set|\{\}|\[\])" src/store src/utils src/hooks`
  の結果とつき合わせる（作成の機材の段の入力が残り、再起動せずに次の人がログインすると前の人の商品名が戻った）
  初期値を書かない `let x: T | undefined` もこの grep に掛からないので、`^let ` だけでも一度引く
- **戻ってきたとき（フォーカス）に、表示中の値を空にしてから非同期で読み直していないか** — 読み終わるまでの
  数フレーム、行が消える・並びが跳ぶ。開いてすぐ閉じる操作でいちばん目立つ。古い値を一瞬出さない目的なら、
  空にするのではなく、書き込みが通るストアにメモリの控えを持って同期で引く
  （マイデスク一覧が戻るたびに作成途中の控えを null にしていて、「作成を続ける」の行が一瞬消えた。
  データの観点は保存値の食い違いしか見ておらず、読み直しの間の表示は拾えなかった）
- **遅れて届いた読み込みが、後から始めた読み込み・操作の結果を上書きしないか** — フォーカス・切り替え・
  引っぱって更新で始めた取得は、届いた時点で `setItems` する前に「まだ最新の依頼か」を確かめる
  （`requestIdRef`。先例は `DeskFeedScreen` の `loadRequestRef`）。解除・× などの操作は、それより前に始まった
  取得の結果を捨てるか、結果から抜く。`grep -rlE "useFocusEffect\(" src` の結果のうち
  `requestIdRef|requestTokenRef|alive|cancelled` を含まないファイルを読む（履歴の「見た／拍手した」を素早く
  切り替えると、2往復する拍手側があとから届いて「見た」の下に並んだ。保存の解除も、戻った直後の読み込みが
  解除前の一覧を返してタイルが戻った。件数が増えて応答が遅いほど起きる。直前の観点は空にする向きしか
  見ておらず、遅れて届く向きを拾えなかった）。あわせて、件数に上限の無い一覧が1件ごとに大きい列
  （`share_snapshot`）を全件引いていないか、上限を行で切って表示の単位（デスク）とずれていないかも見る
- **同じ切り替え操作（拍手・保存・フォロー）を別の一覧に足したとき、元の実装の守りを全部持っているか** —
  「戻ったら読み直す」「状態が分からなければ先に引く（分からないまま反転しない）」「送信中・押した後に
  届いた読み込みで上書きしない」の3つを、送信関数の呼び出し元（`grep -rnE "setDeskLiked\(|setDeskBookmarked\(|followUser\(|followBrand\(" src`）
  ごとに表にする。件数を出す操作は、手元の ±1 を正にせず、送り終えたらサーバーの件数で合わせ直しているかも見る
  （一意制約違反を成功扱いにする送信や、0行の削除がエラーにならない RLS では、成功で返っても件数が動かない）。
  履歴・保存のタイルの拍手（`useDeskClaps`）はみんなのデスクの3つの守りをどれも持たず、詳細で拍手して戻っても
  古いまま・読む前に押すと件数だけ +1 になっていた。これまでの観点は「片方の画面にだけ入った修正」を
  探す向きで、後から足した側が元の守りを持たない向きを拾えなかった
- **機能フラグで入口を閉じたとき、閉じた側の関数にだけあった処理が新しい道に移っているか** — 前の画面が
  params で渡した前提（ジャンル・名前）、計測（`trackOnce`）、日付などの既定は、閉じた入口の関数に書かれていることが多い。
  フラグ名で `grep -rn "<FLAG>" src` を引き、false の分岐の下でしか読まれない state・params と、到達しなくなった関数の
  中の副作用を並べる（`PRODUCT_BROWSE_ENABLED` を閉じて「ジャンル→詳細設定」の道にしたとき、配線図の「○○を登録」・交換が
  渡したジャンルを捨てて選び直させ、`first_item_added` も送られず、導入日の「今日／不明」も聞かなくなっていた。
  「上限を入口でだけ守っている」は判定の取りこぼししか、「説明文が指している操作」は文言の一致しか見ておらず、拾えなかった）
- **補った値・まとめた値で「無い」「範囲内」を判定していないか** — 表示のために足した値（「今日」ページ・
  登録日で代用した導入日）を足した後の配列で空・未入力を判定すると、その分岐に二度と入らない。
  期間でまとめて最大の日付を代表にする処理は、未来・範囲外の日付が1件混ざると期間ごと外へ出る。
  補う・まとめる処理の出口で、元が空だったか・代用かを印か別の値で残しているか、判定がその前の値を見ているかを確かめる
  （歴史カードは今日を足した日付で空を見て「1年より前は Pro」を出せず、年表は登録日の代用を購入日ありと
  読み、月ごとの再生は予定の撤去がある月を丸ごと落としていた。「読めなかった」と「0件」の観点は
  読み込みの失敗しか見ておらず、正常に補った値が判定を潰す向きを拾えなかった）

## 2. 報告（修正の前に一度止まる）

見つけた問題を**深刻度順**に並べ、各項目について：

- 症状（どの操作で何が起きるか）
- 根本原因（ファイル:行）
- 対症療法ではない修正方針

推測で「たぶんここが原因」と書かない。コードで裏を取れなかったものは、そう明記する。
問題が見つからなければ「無い」と言い切る。無理に絞り出さない。

## 2.5 原因の横展開（報告に必ず含める）

根本原因を特定したら、それを**パターンとして1行で言語化**する。
例）「useEffect の依存配列に lang が入っていない」「`??` で旧データを既定値に握りつぶしている」

言語化したパターンで**コードベース全体を検索する**。対象領域の外で見つかっても報告する。
「この領域には無い」で閉じない。1件見つかった時点で、同じ書き方が他に何件あるかを
数えるまでが調査。

報告には次を必ず含める：

- パターンの説明（1行）
- 検索に使ったクエリ（`grep` のパターンをそのまま書く）
- 該当箇所の一覧（対象領域の外も含む）と、それぞれが実害を持つか否か

「他にもありそう」で終わらせない。検索していないなら、していないと書く。

## 3. 修正

承認を得てから直す。

- 症状を隠す修正（表示側での握りつぶし、条件の後付け）はしない。原因の層で直す
- 頼まれていないリファクタを混ぜない
- 直したら `npx tsc --noEmit` を通す
- 配線図の計算に触れた場合は `src/utils/mapLayoutCache.ts` の `LAYOUT_VERSION` を上げる
- 実機確認が必要な項目は、確認手順を具体的に書いて渡す

## 4. 観点の更新

過去に同じ領域を `/bug` で調べているのに漏れていた問題が見つかった場合、
**「なぜ前回の観点リストで拾えなかったか」を1行で書き**、その観点を §1 のリストに
追記してから終わる。追記しない場合は、しない理由を書く。

観点は使うたびに増えるもので、固定のチェックリストではない。
